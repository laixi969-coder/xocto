  但在这之后，即使某项单点开发任务获得五倍、十倍的提速，一个项目从需求提出到产品交付的速度，有时候未必能有两倍效率提升。 时间去了哪里？ 写提示词、等待 AI 生成是一部分；生成效果不理想，手动在 IDE
  中 修改是另一部分。甚至，开发完成后，代码还需要打开终端测试；准备项目汇报，又要切换到文档和演示工具。 每换一个应用、开启一段新会话，都可能需要重新解释：项目在做什么，为什么这样设计，刚才改到了哪里，还有哪些问题没解决
  。 AI 的生产力跑在了前面，而承载它的开发基建：任务调度、状态管理、验证闭环、产物沉淀、跨工具协同，还停留在前 AI 时代 。 于是，到了 2026 年，一些变化开始发生了。这一年，AI 个人助理赛道的热度彻底走到了爆发节点：Meta
  推出的个人助理 Muse 上线两周便登顶美加 iOS 免费榜，下载量突破 340 万；此后，OpenAI、Google、字节、腾讯、阿里均在加速落地个人助理类产品，短期内上百玩家如雨后春笋冒出。然而，噱头大过了实际，多数生活场景并不存在所谓的标准版答案，也导致真正帮助用户解决实际问题的产品寥寥无几。
  为数不多的例外来自编程，以 TRAE 为例，前不久将 TraeCode 与 TraeWork 合并之后，10 月 29 日，平台又正式上线开发者个人助理 TRAE，可以 跨项目理解历史上下文，也可以在单个项目里拆解、并行、统筹多个任务。
  对开发者来说，从此开启新任务时不再从零解释；完成复杂项目推进时，也不再自己拆任务、切会话、盯进度、拼结果。 这一次，工作流的进化，终于赶上了 AI 生成的速度。 01 AI Coding 的工作单位，
  在从一条指令升级为一个项目 AI 编码工具的进化，到今天刚好走完三代。 第一代是补全时代。Tab 键自动补全、函数级生成，本质是编辑器的增强，人主导每一行，AI 做填空。它提升的是输入速度，改变不了工作流。
  第二代是单会话 Agent 时代。开发者说一句需求，AI 自己读文件、改代码、跑命令，能端到端做完一个小功能、跑出一个 Demo。但它仅限于完成单次会话、单个任务、上下文随会话结束清零，复杂一点的多线程任务，还是要人来拆解、跟进，做结果拼合与修改。
  以全新的 TRAE 为代表，行业正式进入第三代，即项目级助理时代。 AI 开始拥有任务调度权和状态记忆，可以自己拆解复杂需求，派发多个子任务并行执行，自己完成编译、测试、验证的闭环，并且跨会话、跨项目记住做过的事、产出的文件、踩过的坑。
  具体来说，与此前 OpenAI 完成 ChatGPT 与 Codex 的合并，Cursor 3 推出了专门的 Agents Window，把 Agent 管理从编辑器侧边栏独立出来类似，TRAE 先是将做编排的
  Agent 模式与做开发的 IDE 模式整合，让它们可以同步本地任务对话、最终产物及相关配置。 在此基础上，又借助全局助理「全局 TRAE 宝」+ 项目助理「项目专属 TRAE 宝」的双层架构，把跨项目记忆和单项目并行调度落地到了本地仓库场景。
  如此一来，开发者可以先在工作台里描述目标，由 Agent 完成拆解后，全局助理与项目助理会承接具体的开发，当开发者需要检查具体实现时，又可以再进入 IDE。 再加上配套的模板库、插件市场、自动化任务和产物管理等能力，AI
  的工作单位，已经逐渐从一条指令升级为一个项目。 02 实测：TRAE 开发者个人助理 究竟节约了多少真实开发中的垃圾时间 理想很丰满，但所谓的跨项目记忆到底有没有复用价值，个人项目助理又能不能真的完成真实场景测试，我决定用一个真实复杂项目做个测试。
  这次，我选了 B 站开源的 Go 微服务框架 go-kratos/kratos（GitHub 2.6 万星）。 选择它，是因为这个项目有足够多的上下文负担。 HTTP、gRPC、中间件、服务注册发现、配置中心，分布在十几个目录中。一个
  HTTP 请求进来，监听和路由由 transport/http 负责，日志、熔断、限流等通用能力则在 middleware 中实现。想写出能用的代码，首先要理解这些模块如何配合。 此外，这次测试的仓库主干已经使用
  github.com/go-kratos/kratos/v3 包路径。如果 AI 沿用过去熟悉的 v2 写法，没有读取当前仓库的配置与源码，生成的示例就可能无法编译。 而针对这样的需求做 AI 开发，过去开发者往往需要先手动找出核心文件，解释模块关系，把相关代码贴进对话框。接下来，写代码、补文档、跑测试，如果分成几个会话，又要自己同步背景、跟进进度、汇总结果。
  代码生成之前的准备，以及生成之后的收尾，构成了开发中大量零散、重复的时间开销。 所以，这次实测，我把架构梳理、示例开发、测试验证和后续维护放进同一条工作流，看看 TRAE 究竟能帮我解决多少实际问题。
  第一步，开通全局 TRAE 宝，然后按照我的个人偏好，给它改名。 先去模板库和插件市场完成工具配置。 进入项目之前，我先看了 TRAE 的模板库和插件市场。模板库按内容创作、数据分析、办公协同、产品开发、战略与研究等场景组织案例。选择模板后，输入框会带入结构化指令；「应用开发」「项目理解」「工具脚本」等入口，也能帮助开发者快速组织任务。
  当我们的需求包含多个交付物时，它可以先给出一份相对完整的任务骨架，减少从零组织提示词的成本。 比如要做技术选型或立项，直接点选模板，输入框里会自动填好结构化指令（像图里的 @采购分析 调研筛选 5 家大模型供应商，为
  AI Token 采购立项制作价格、能力和预算对比）。 接着，我又在插件市场为后续流程安装了「代码审查报告」和「飞书」插件，前者用于检查代码改动，后者用于连接云端文档。 准备以上完成后，就正式打开 kratos
  的项目助理，处理真正的开发任务。 进入项目后，助理先读取本地仓库，识别了 transport、middleware、registry、contrib 等核心目录。过程中，我没有逐个复制文件，也没有先手写一份项目背景说明。
  随后，我一次性提出了三个要求： 梳理 transport/http 与 middleware 的职责，生成说明文档，重点解释 HTTP 层的 FilterFunc 与框架层 middleware.Middleware
  的执行时机。 增加一个最小可编译的 HTTP handler 示例，使用当前仓库的 v3 包路径，并说明如何接入 App 的生命周期管理。 运行相关包的测试，说明测试范围，以及项目已有的 Makefile
  和 CI 如何执行测试。 这三个任务共享项目背景，又分别涉及源码理解、代码实现和运行验证，很适合观察项目助理能否完成拆解与统筹。 TRAE 先执行了 6 条命令了解仓库结构，随后启动三个子任务，并行推进文档、示例和测试。
