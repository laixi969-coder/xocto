## 一句话定位

把一群普通电脑组成一个点对点（P2P）集群来跑超大规模 MoE 模型——
你的机器出磁盘、别人的机器出算力，大模型界的 Napster。

## 做这个东西的人

GitHub 用户 JustVugg（HN 用户名 vforno），个人开发者，Apache-2.0，纯 C 实现。
项目 2026-08-04 建仓，10 天内 80 次提交，目前 47 star / 2 fork。

它不是一个新起点：作者先做了单机版 Colibrì（一台普通电脑能不能跑超大 LLM，
同样靠 MoE 稀疏激活的思路），Lumabri 是把同一个问题从单机搬到多机。
HN 上的第一帖"Show HN: Lumabri – What if LLMs worked like Napster?"只有 8 分 10 条评论，
作者在帖子里自述没有数据中心、没有 GPU 集群，用手头硬件做实验。

_判断：这是典型的个人极限工程，不是商业项目。真正的信号是作者的两步路径——
先用单机证明 MoE 可以省着跑，再问"多台普通电脑能不能拼成一台巨型电脑"。
这个提问顺序本身比代码更有价值。_

## 它到底能做哪几件事

- **P2P 权重分发** → tracker（索引）+ maintainer（字节范围管理）+ `liblumibri.so`
  （LD_PRELOAD 垫片，实现稀疏本地镜像：只缓存访问过的数据块），对端出问题时自动故障转移
- **远程执行专家层** → `expert_node` 持有某几个 MoE expert 的权重，别的节点把
  激活值（activation）传过来、远端算完再传回去，**权重不出本机**
- **对抗网络延迟** → 距离地图、就近副本优先、预读（prefetch）、副本故障转移
- **两种信任模型** → 开放群靠 SHA-256 校验防投毒；邀请群用 `LUMABRI_TOKEN` 控访问；
  `LUMABRI_VERIFY` 会在第二个副本上抽查专家调用并要求输出字节级一致
- **传输安全** → X25519 + ChaCha20 加密、身份固定、防重放；v2 协议加了签名检查点、
  防崩溃镜像、连接门控

**关键承诺是字节一致性**：README 声称已在 OLMoE、GLM、Inkling、Kimi K3、
DeepSeek V4 上验证过"远端执行和本地执行输出字节级相同"。

## 它在替代什么旧行为

要跑千亿参数的 MoE 模型，以前只有一条路：租或买足够大的 GPU 集群。
成本按月计，普通人碰不到。

Lumabri 主张的替代路径有两条：
- 用局域网里几台普通电脑拼起来，替代"单台机器 + 超大显存/内存"（甚至替代磁盘换页——
  作者实测在模拟局域网里 P2P 专家执行 5.97 tok/s，对比磁盘直读 0.04 tok/s，声称约 149 倍）；
- 用互联网上的捐赠节点拼一个 swarm，替代云端 GPU 服务。

**但它替代不掉的东西要明说**：P2P 分布式推理不是新问题，Petals 这类项目做过多年，
始终没有真正进入生产。作者在 HN 里被 hazard 用户点名三大根本问题——单卡装不下
单个 expert、跨节点激活值传输让每个 token 慢到数百毫秒、P2P 网络里除了重复计算
没有可靠的防作弊手段（SHA-256 签的是文件不是计算结果）。这三个问题 Lumabri 的
README 都没有给出答案。

## 商业模式

**无。** 纯开源实验，没有云端服务、没有定价页、没有任何收入接口。

_判断：这个问题不值得问——它连"要不要商业化"都还没走到。_
_值得问的反而是：如果有一天 P2P 推理真能成立，钱的形态会是节点贡献者的激励
（类似 Bittensor 的押金与罚没），而不是软件授权。现在谈这个太早。_

## 判断

**这是"大模型分发的基础设施猜想"，不是产品。** 值得看，但要按猜想的规格看。

三个点值得记住：
- **Napster 类比不是营销**。P2P 历史上真正活下来的场景（文件分发、CDN）
  都是"读多写少、内容可校验"，MoE 推理恰好是"内容可校验、读多写少"，
  类比比表面上有道理。
- **字节一致性是最有价值的技术主张**。它把一个"能不能信对等节点"的问题
  降维成"输出不一致就有一方在撒谎"，配合抽查，是 P2P 推理里少见的可执行设计。
- **但它替代不了 GPU 云的真正理由不是技术**。是对等节点没有 SLA、
  没有激励、没有责任。这个问题的答案在 token 经济里，不在加密里。

**给"有待观察"而不是"值得关注"的原因很直接**：热度低（HN 8 分）、
无商业模式、三大死穴一个都没解决。但如果三个月后它能证明"互联网规模的
swarm 真能跑出可用速度"，那它的架构笔记值得逐行读。

## 下一步看什么

① 有没有独立的第三方（不是作者自测）在真实互联网延迟下复现速度数字
② 节点贡献激励有没有出现（没有激励的 P2P 推理历史上从未跑通）
③ star 与社区讨论能不能起来——起不来说明连开发者圈子里也没人信这个方向

## 可借鉴的做法

**产品逻辑**：当你手里有一个"内容可校验、读多写少"的重计算任务时，
可以认真考虑把计算外包到网络里——它比租 GPU 便宜，且校验成本低。
反过来，如果你的计算任务结果不可校验（生成式、主观判断），P2P 外包这条路
直接划掉，防作弊的成本会把收益吃光。

**话术**：无。README 是工程文档，没有可偷的句式。

**定价结构**：无。未披露。
