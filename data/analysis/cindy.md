## 一句话定位

把 Claude Code、Codex 这类各立山头的编程 agent 收进同一个工作区：
任务中途随便换模型换 harness，记忆、技能、上下文不丢，
桌面、手机、IM 三端都能接管同一个 agent。

## 做这个东西的人

开源项目，GitHub 组织 `makecindy`，背后是心动公司（TapTap 联合创始人黄一孟）——
2026-07-22 在 TapTap 开发者沙龙（TDW 2026）上首次发布。源码 Apache-2.0，TypeScript 写的 monorepo，含桌面端和移动端客户端。

_判断：一个游戏平台下场做通用编程 agent 客户端，动机不是做工具，是做生态入口——
TapTap 上半年新发行可玩游戏 5002 款、超 4000 款靠 AI 制作，AI 已经把游戏供给量推高了一个数量级。
Cindy 是他们押注的"AI 工作环境"，游戏发行那套分发逻辑被搬到了 agent 上。_

## 它到底能做哪几件事

- **多 harness 统一工作区** → Claude Code、Codex、Pi 三套执行环境已接入，原生 harness 在开发中；任务中途可切换，工作区、记忆、技能、工具保持连续
- **多 agent 编排** → 一个任务可拆成"规划 + 多 worker 并行执行 + 独立审查"三个角色，跨 harness 接力
- **开箱即用** → 免登录本地模式、自带 20+ 工具，四种接法（官方托管服务 / 已有 Coding Plan / 自己的 API Key / 本地模型）都直接可用
- **跨端遥控** → 手机远程接管电脑上的任务、Slack/飞书里 @ 它派活、定时任务跑完回报到 IM
- **信任控制** → 隔离工作区、逐行审查、可回滚 checkpoint、默认不上传整个项目、实时显示成本

**它明确不做**：不造自己的大模型（接 GPT/Claude/Grok/Gemini/DeepSeek/Kimi/GLM/Qwen），不强行让你为同一个模型付两份钱。

## 它在替代什么旧行为

以前用编程 agent 是"一人一套独立环境"：Claude Code 一个终端、Codex 一个环境，各有各的 workspace 和记忆，想换模型等于重起炉灶；想从手机远程看一下进度，基本做不到。

Cindy 替代的是三件事：一是**多 agent 的切换成本**（中间态 → 同一工作区随时换），二是**装机配置成本**（配 API Key、配环境 → 免登录本地跑），三是**"人在电脑前才能用"的约束**（手机/IM 就能指挥和审批）。

## 商业模式

客户端免费（Apache-2.0），核心逻辑是"欢迎你用已经买过的订阅，不重复收费"。收入来源：

- **PLUS $20/月起**：官方托管模型服务，GPT/Claude/Grok/Gemini/DeepSeek/Kimi/GLM/Qwen 统一网关，月付省 20%，更高档位 SUPER/ULTRA
- **TEAM（coming soon）**：SSO、集中配置、信用额度、团队技能分发
- **ENTERPRISE（联系销售）**：网关自托管进 VPC、审计日志、成本归属

_判断：这套"免费软件 + 卖托管服务 + 卖企业管控"的三层结构和 n8n、Supabase 验证过的路子一致，但多了个有意思的细节——**允许复用订阅**。这不是大方，这是获客：他们赌的是托管服务的便利性会让人逐步迁过去。_

## 硬数字

- 心动 CEO 在发布场合披露 TapTap 上半年新发可玩游戏 5002 款、同比增长 843.8%，超 4000 款借助 AI 制作（官方口径，无第三方验证）
- 团队对外自述：心动内部美术同事可经 Cindy 直接提 PR、程序直接发布优化（官方自述，外部未验证）
- 用户量、ARR、融资：未披露
- 756 个 open issue 相对 1995 star 偏高——社区需求旺盛，但也说明版本成熟度还在早期

## 四维评估

| 维度 | 结论 |
|------|------|
| 创始人-产品匹配度 | 心动自己是 AI 游戏生产重度用户，内部已在用；但这更像平台战略项目而非创始人项目 |
| 产品洞察力 | 抓住了"切换成本"和"开箱即用"两个真痛点；"复用已有订阅"的获客设计比免费还狠 |
| 技术实现质量 | TypeScript + React Native/Electron 跨端，本地优先、隔离工作区，工程结构规范；但 756 个 open issue 说明还远未稳定 |
| 市场时机 | 正好踩在 agent 从单模型走向多模型混用的拐点上；但同赛道挤着 Claude Code、Codex 官方客户端和一堆开源竞品 |

## 判断

**这是游戏平台把"分发生态"的逻辑搬到 agent 上的实验，目前最有想象力的部分是获客设计。**

"支持已有订阅不重复收费"听起来是让步，实际上是标准打法：让用户零迁移成本进来，
再靠托管服务（多模型统一网关 + 省 20%）把量一点点从自带 Key 挪到官方账单上。
这个转化路径对读者有直接参考价值。

**多 harness 切换是真差异化。** Claude Code 和 Codex 各有所长，官方互相不打通，
Cindy 赌的是"连续性"比"单点最强"更重要——这个判断对多 agent 混用的团队成立。

**风险在两端**：一是生态层面，Claude Code 和 Codex 官方每迭代一版，Cindy 都要追着适配，追不上的那天就废了；二是商业层面，它主场的游戏制作场景（TapTap 制造）才是它真正的护城河，通用编程 agent 市场未必打得过官方。

## 下一步看什么

① 三个月后 stars 是否过 5000——早期增速有没有变成持续趋势
② open issue 数能否压下来——756 个积压说明稳定性还没兑现，指标是 issue 增速低于 star 增速
③ 是否有第三方团队公开报告在生产环境使用（而非仅 TapTap 内部自述）

## 可借鉴的做法

**产品逻辑**：做"绑定生态"的工具时，"承认用户已有的付费并主动复用"比"免费"更有效——降低迁移成本到零，再靠托管增值项慢慢转化。这是反直觉的获客设计，可以抄。

**话术**："Reuse the subscriptions you already own" —— 把"不重复收费"写成一句主张，比"免费"更有记忆点。

**定价结构**：三层定价（免费自备 Key / $20 托管 / 企业自托管）可以直接抄，尤其是"月付省 20%"这种把 API 转售包装成省钱方式的写法。

## 结论

**值得关注，但有明显的不确定性。** 背景硬（心动/TapTap）、增速快（三周近 2000 star）、获客设计聪明，但产品成熟度（756 open issue）和生态依赖（追官方适配）都是硬伤。记下上面三条，三个月后回来验证。
