03

60 秒生意判断

先给出判断与下一步，再保留完整证据和反例。

一句话定位

一个自定义标签 <tear-line>，把你已有的 HTML 包起来就变成一张带锯齿撕边的热敏收据，再一键导出 PNG——不是模板语言，也不是图片服务。

做这个东西的人

Isaiah Kim（HN/GitHub: kyisaiah47），独立开发者，托管在他的个人站点 kynth.studio 下。这是他的开源项目，MIT 协议，零依赖，单文件。

判断：这是"为了自己做个收据生成器，结果做成了通用组件"的典型。文档（dom-to-png、share-image-custom-element、receipt-ui、spotify-receipt-generator）写得比大部分商业产品还全，作者是真把技术问题抠透了。

它到底能做哪几件事

  • 包任何 HTML：标题、表格、图片、列表，渲染成热敏收据样式——撕边、条形码、纸张质感
  • 一键导出 PNG：el.download() / el.toBlob()，任意缩放
  • 真实文本不是 canvas：收据是 light DOM 里的真实文本——可选中、可搜索（⌘F）、可翻译、屏幕阅读器按文档顺序读
  • 确定性渲染：撕边和条形码由 seed 决定，同一个 seed 永远渲染成同一张纸，导出图和用户看到的一致
  • 零依赖、零构建：任何框架（React/Vue/Svelte/原生 script 标签）都能用
  • 附带四篇深度技术文档，其中一篇直接推演了"Receiptify 式应用为什么做不起来"（Spotify 五用户上限卡死大多数这种应用）

它明确不做：条形码不扫描（纯装饰）、不做服务端图片服务；收据内的图片必须是 data: URI（SVG foreignObject 无法联网，作者在导出时会直接报错而不是交一张带洞的图）。

它在替代什么旧行为

以前想让订单摘要、年度回顾、歌单变成"一张收据图"，只有两条路：

  • 用 html2canvas 这类库在浏览器里截图，结果经常是 tainted canvas 一片空白，或者截图和用户看到的对不上
  • 起一个 puppeteer 截图服务或付费图片服务 API，每个收据模板都要写服务端代码、付服务器钱

Receiptify 现象是这里最好的注脚：人人都喜欢"收据式分享图"，但做这种应用的人全死在 API 限额上。tearline 把生成收据这件事压成"一个标签 + 浏览器本地导出"，服务端整个消失了。

商业模式

免费。 MIT 协议，零依赖，无账号无服务器。没有商业形态，也不打算有。

判断：这就是个高质量开源组件，价值在作者（他靠作品建立个人品牌）和使用者的零获取成本。对读者，它没有商业模式可分析，但有格式洞察可偷。

硬数字

  • HN 6 分 / 0 条评论（2026-08-13）
  • package.json 的 dependencies 为空，单文件 ES module，无构建步骤
  • 授权：MIT；下载量、npm 安装量：未披露

判断

这个产品最值钱的是它验证了一个格式洞察：收据是比截图更天然的分享物。

订单、歌单、年度回顾、体检报告——人类已经习惯了"收据"这个信息载体，套上它，一张表格截图就变成了"值得发出去"的东西。Receiptify 的爆火证明了需求，tearline 证明了这个需求可以用一个标签的成本化解决。

可迁移的规律：找一个用户已经熟悉到自动想要分享的"旧格式"，把新功能套进那个格式里。 收据、登机牌、体检单、证书——都是"表格数据 + 仪式感排版"就能变成传播物。你的产品如果有一块"用户想展示的数据"，值得想想该套哪个旧格式。

问题：格式洞察可偷，但组件本身没有商业空间——不收费、不托管、代码量小到抄起来没负担。它是一枚好零件，不是一门生意。

下一步看什么

① npm 下载量 / GitHub star 增长——说明格式被多少人真正使用 ② 有没有人用 <tear-line> 做出热门分享图应用（Receiptify 的替代品） ③ 作者会不会把它升级成托管服务

可借鉴的做法

产品逻辑："收据/票根/证书"这类旧格式是天然分享载体——把用户想展示的数据套进仪式感格式，分享意愿会凭空涨一截。做 AI 产品的人可以用这个思路做分享卡片，而不是再做一个平平无奇的结果页。

话术："任何用户想保留或晒出去的东西：订单、训练记录、年度回顾、预订、歌单、一份 diff"——用"想保留或晒出去"作为功能筛选标准，这一句可以直接借用。

定价结构：无。免费 MIT。

结论

有待观察。 工程质量是这批里最好的之一，但没有商业模式。把它当作"收据格式"这个传播洞察的证据留下来，三个月后看有没有人拿它做出热门分享应用。
