怎么做产品：可迁移的方法论

  • stoaexchange 不做撮合，先做基准。 先让所有人都来看你的价格，来的人多了，交易自然发生在你这里。 这条对任何「信息不对称严重、单笔金额大」的行业都成立 —— 地产、二手设备、大宗商品，结构和 GPU 是同一个。 基础层重点研究
  • deepseek-harness 如果你正站在「平台 vs 工具」的岔路口，可以照这个分层法——把核心循环做成可替换层，模型、工具、UI 全部插件化，先亏着把壳送出去，再在另一层（模型调用）的用量上收钱。前提是另一层边际成本够低，且你承受得了生态初期的质量参差。 基础层重点研究
  • qm 多 Agent 工作流要从「一个人用」变成「团队用」， qm 的分域结构值得参考 —— 每人一个隔离工作区 + 一个共享技能库 + 管理员定可用模型。 这三件事的组合，比做一套权限系统简单得多，效果一样。 AI + 效率重点研究
  • shuohao-skills 它把「从小说到可开拍素材」这一段做成了标准件， 补的正是所有「从灵感到成片」类工作流都缺的上游环节。 它的 13 道质量门尤其值得看 —— 把创作质量变成脚本能检查的硬约束， 这个思路可以搬到内容流水线的每一个环节上。 AI + 创作重点研究
  • open-ai-canvas 去读它的角色资产数据结构 —— 它怎么定义一个角色的「外观、声音、气质」，并让这些在不同生成环节间保持一致。 这是所有「从文字到成片」类工作流最核心也最难的一段，现在答案公开写在 GitHub 上。 AI + 创作重点研究
  • Gendangzou-skill 最值得看的是它的四线交叉结构 —— 政策、媒体、市场关注、资金确认， 四条独立线索验证同一个判断。这个结构比任何单一信号都稳， 而且不限于股票：地产的政策、舆情、成交、资金，是同一个模型换一套变量。 基础层重点研究
  • AI Group Call 如果"讨论"是你的产品形态，别只给一个 AI 角色—— 给一组带立场冲突的角色，并让用户能实时改角。多立场碰撞的价值大于单角色 的"更聪明"，因为用户要的是过程，不是结论。 AI + 效率持续观察
  • AI 搜索｜百度 存量入口做 AI 化时，抄它「灵感探索」的分法—— 不要把搜索做成「一次问答」，把问答做成「带着用户往下想」。 在回答旁边给延伸方向、问题脉络和相关链接，让用户留在同一个页面上， 而不是答完就走。这个动作让 AI 从「回答工具」变成「思考引导」。 通用助手持续观察
  • AdmitRaven "小课+打卡+锁手机"是治疗"拖延型焦虑"场景的通用配方—— 用户不缺信息，缺执行。把大任务拆成每天 10 分钟、用连击给正反馈、用锁屏 给负反馈，这套机制可以搬到任何"重要但没人逼你"的事上。 AI + 生活持续观察
  • AgentOne Desktop 做给非开发者的 agent 工具，入口应该是"一句话描述目标"， 而不是"配置流程"；配置退化成可选项而不是前置条件。这个先后顺序本身 就是产品定位。 AI + 效率持续观察
  • Agnes AI 如果你的产品既有 AI 能力又要多人协作，值得抄它的分法—— 把「文件」和「语境」分开交付。文件层用成熟的协同编辑， 语境层用 AI 自动沉淀背景、决策和引用来源，让后加入的成员不用从头问起。 这是飞书 / Google Workspace 没覆盖的空位。 AI + 效率持续观察
  • Alphabet Soup 做轻量多人游戏，规则要让"一局短、胜负明确、围观友好"—— Alphabet Soup 用"最长词"替代"最多词"，把游戏从个人练习变成 可围观的对决。多人产品的核心设计目标不是深度，是"随时能叫上人"。 AI + 生活持续观察
  • AndroMeld 想找市场缝隙，先去大厂生态里找"已经被教育好的体验"， 再把它翻译到另一个生态——用户不需要被教育，只需要被迁移。 补缝产品最好的起点是"对面已经有了"。 AI + 效率持续观察
  • Ante 如果你的工具面向"并行跑很多 agent"或"隔网环境"两个场景之一， "单二进制 + 零运行时依赖 + 可选本地推理"是值得复制的架构决策；但要先想清楚 闭源 vs 开源的信任成本——承诺离线隐私的产品，不能给用户一个无法审计的二进制。 AI + 开发持续观察
  • Argos 做需要用户交出账号权限的产品，先解决信任问题再谈功能。 三个动作可以照搬：破坏性操作（发送/提交）前必停问；执行后验证真实后果而不是信事件触发； 把权限边界写清楚（什么上传、什么不碰），别用"数据留在本机"这类模糊承诺。 AI + 效率持续观察
  • AstraPixels 做"卖一次"的数字产品时，给它设计一个"内容每次都在变"的机制—— AstraPixels 是实时轨道位置，你的产品可以是实时数据、实时榜单、实时内容。 让每次打开都不一样，是解决"买完不再来"的通用方案。 AI + 生活持续观察
  • Basedash Subscriptions 产品功能清单里永远留一个"送达"位——数据/报表/通知，不只是生成， 还要想"怎么到点送到人面前"。参考它的结构：自然语言节奏 + 投递时实时渲染 + 接收人可选 + 深链回实时版。 AI + 效率持续观察
  • Bullet 任何效率类产品都该问"最贵的一环在哪"。Bullet 的回答是往返次数，而不是模型 速度。做一个 agent 产品或效率工具前，先数一遍你的管线里有多少次串行等待——这是最容易被 改掉的成本。 AI + 开发持续观察
  • Claude by Anthropic 把「重复性知识工作」做成可委派的动作。 Claude Code 教的不是「写更多代码」而是「把什么交给 agent」—— 修技术债、升依赖、跑验证这类规则明确、量大、不依赖创造力的工作， 是最先适合自动化的部分。这个「先挑规则明确的活」的顺序可以迁移到任何工作流。 AI + 效率持续观察
  • CodeBuddy｜Tencetn 做开发者工具时，「全形态覆盖」不是炫技而是覆盖不同人群—— 插件给日常补全（手动挡），IDE 给非技术用户（自动挡）， CLI 给专业开发者（赛道模式），底层模型和额度打通， 用户随场景切换不重复配置。如果你做工具，先想清楚三类用户 各自在哪个入口，而不是只做一个形态。 AI + 开发持续观察
  • CodeBurn 当你的用户已经在产生某种数据、只是没人读时，先做"读现成数据"的工具，比做"要求用户先埋点/先装探针"的工具省十倍的推广成本。CodeBurn 一行 `npx codeburn` 就读完全部历史，这是它爆发的第一因。 AI + 开发持续观察
  • DSH-better-sidebar 如果做 chat 型 AI 产品的配套环境，别急着做完整 IDE，先做"侧边栏工作台 + 按需加载"：核心保持轻（325KB 级），重依赖（Office 预览、终端模拟）等用户真打开那类文件才加载。这样产品声称"完整工作台"时不会把首屏拖垮。同时把"第三方可注册新面板"作为第一版就有的能力，让生态替你长功能。 AI + 开发持续观察
  • DeepSeek 事件驱动型产品（强发布、弱日常）要接受流量的大起大落， 别拿日常运营补——补也补不回来。把预算押在「下一个高光时刻」 比押在增长黑客上更划算。 通用助手持续观察
  • DeepSeek - AI 智能助手 如果你做的是「工具型」产品（用户用完就走），抄它的入口 分法——网页端做深度主场，App 做移动端补充，但不要指望 App 单独 拉来泛用户。工具型产品的用户增长靠「高光时刻」驱动 （模型发布、话题事件），日常增长有限，预算要跟着这个规律走。 通用助手持续观察
  • DeterminFlow 任何一个"让 AI 干正事"的产品，都可以把"一次跑通"和"跑断了能接着来"当成两个独立卖点来设计。前者决定演示效果，后者决定客户敢不敢把真活交给它。DeterminFlow 把可恢复做成了第一卖点，而不是事后补丁，这是它和同类拉开差距的地方。 基础层持续观察
  • Devin 挑「规则明确、量大、不需要创造力」的活先自动化 （技术债、依赖升级、批量修改），这是 agent 唯一能稳定交付的区间。 Devin 的经历同时证明：别把能力吹到 demo 之上—— 一次性信任崩塌后，要用一整个版本的诚实才能重建。 AI + 效率持续观察
  • DocsAlot CLI 如果你的产品是给人用的工具，可以学它把"agent 作为第一用户"当作一等公民来设计——agent 能读懂的指令文档 + 托管 MCP 端点，等于免费把自己的产品接到了每个编码 agent 的工作流里。这是成本极低的渠道。 AI + 开发持续观察
  • Dograh 如果要做"开源替代闭源"，先列一张竞品用户最痛的三件事（价格、数据主权、锁定），然后只攻其中一件，而且只对那一件的目标客户说话。Dograh 把全部火力放在"数据不出边界"上，连界面文案都在讲 HIPAA/GDPR/SOC 2 场景。 基础层持续观察
  • DuckDisk 做任何分析型工具，先写出一张"用户会问的问题清单"，再用数据形态去逐条回答。DuckDisk 的整张表就是 5 个问题的答案集（谁占空间、分配多少、占父级多少、几个文件、什么类型）——表格不是审美选择，是答案密度最大化的结果。 AI + 效率持续观察
  • Git-knife 任何"大家都默认做不到"的操作，值得先验证一下是不是真的没人做——往往只是没人做好。列出主流工具刻意放弃的字段/能力，那里就是空白市场。git-knife 的对比表（工具 × 能力矩阵）是值得抄的调研方法：把自己的位置精确标在别人都打不了勾的那一格。 持续观察
  • Gitar 任何诊断/检测类产品，把"检测出来"和"修好它"之间的那段自动化，就是涨价的空间。Gitar 从"评论"到"改+验证"跨了完整一步；哪怕做不到全自动，做"一键应用修复 + 自动跑验证"也比纯建议强一档。 AI + 开发持续观察
  • Good Assistant 2 任何"帮助用户坚持"的产品，核心杠杆都是"降低用户想起它的成本"——不是功能更强，而是让产品主动出现在用户的注意里（消息、提醒、每日摘要）。做这类产品时，把"如何让用户每天回来"设计在第一天，而不是最后一天。 AI + 效率持续观察
  • Gotcha 给"高风险自动化"设计产品时，把安全模式做成产品功能（只读/可执行两档 + 审计日志），而不是藏在设置里。让用户先放心地试，再决定放权，这比任何权限弹窗文案都有效。 AI + 效率持续观察
  • Grok Imagine 2.0 "编辑"应该围绕真实工作流设计，而不是功能堆叠——它按电商图、头像、表情包、海报给模板，等于替用户预设了使用场景。做 AI 工具时，先列出用户改图的高频动作，再按动作造功能。 AI + 创作持续观察
  • Gutta 做效率工具时，"减少从想法到落地的摩擦"比加功能重要——它把输入路径压到一行快捷键加自然语言，这就是全部设计。任何"捕捉类"工具都该先问：从你想到这件事到它被记下，最快能多快。 AI + 效率持续观察
  • HAR 设计 agent 编排或自动化时，"信任机制"要作为第一等公民：验证结果必须绑定到精确的输入（代码、数据）哈希，而不是 agent 的自我报告。这条原则可以平移到任何"让 AI 自主干活但人类要担责"的场景。 基础层持续观察
  • Hyper3D 做「生成类」工具时，把「生产就绪」当成产品标准而不是 宣传词——用户不关心你生成了多好看的预览，关心的是 「生成的能不能直接进我的管线」。局部编辑、拆分、可编辑拓扑 这些「生成之后还能改」的能力，是工具从 demo 变成生产力工具的分水岭。 AI + 效率持续观察
  • Keet (YC S24) 做"长流程"类产品（学习、调研、项目管理），把"替用户排好顺序"做成显性卖点，而不是只做单点问答。Keet 的课程路线图就是"顺序即产品"的范例。 持续观察
  • Kimi 出海翻译的不是界面，是"价格差+兼容格式"。Kimi 国际站做的关键动作不是英文版 App，而是 API 兼容 Anthropic 格式——开发者换一个 base_url 就能迁移，迁移成本趋近于零。任何要抢存量用户的产品，都应该把"换过来不费力"当作第一设计原则。 通用助手持续观察
  • Kimi｜月之暗面 解释技术参数时，先找一个读者能感受到的数字——"二十万字的小说一口气读完"，比"超长上下文 128K"有效一个量级。参数是工程语言，感受才是购买语言。 通用助手持续观察
  • MCP Memory 做 agent 记忆类功能时，先做"人可读、可审查"的明文存储，再用索引加速， 不要一上来就上向量库。可审计性在 agent 记忆上比检索质量更稀缺。 基础层持续观察
  • MaxAI.me 把高频的"复制-粘贴-切换"动作压成一个手势，是最朴素的效率产品逻辑。做一个工具前先数一遍用户在它要替代的场景里要做几步动作，能省掉两步以上，产品就有了存在的理由。 AI + 效率持续观察
  • Mcptoon 当你的产品依赖一个"必然膨胀"的输入（工具清单、规则文件、 上下文）时，别只做压缩优化，考虑把整个东西挪出主通道、按需取用—— 把"常驻"改成"按需"，常常比优化格式省得多。 AI + 开发持续观察
  • MiniMax - 通用AI Agent 给"聊天助手不产出成品"的缺口造一个独立产品线，并明确告诉用户它与聊天助手的区别（接受目标、拆解、调工具、交成品），而不是混在同名产品里。定义不清是通用 Agent 赛道的普遍病，谁先把区别讲清楚谁占便宜。 AI + 效率持续观察
  • moonlit-stories 「一致性」比「生成质量」更值钱。 它和影策给出了同一个答案：把角色的外观、声音、气质固化成可复用资产， 在所有生成环节里引用同一份。两个独立项目相互印证，比任何单个案例都可信。 AI + 创作持续观察
  • Needle2 当任务边界清晰（映射到有限函数集）时，别默认"越大越好"—— 先问"这个任务需要多少世界知识"。像 Needle 这样把"设备控制"从"通用对话" 里切出来单独做模型，是任务切分的范例。 AI + 效率持续观察
  • Orca 在位者不管的平台（桌面）就是新品类切入点；把产品做成"agent 可操作"（MCP 化） 是 B2B 工具的新接口。做 AI 产品时，"让 agent 直接调用我的产品"应该当成功能规划，而不是加分项。 AI + 商业持续观察
  • Prime Agent 任何"会自我改进"的功能，参考这个安全设计——永久不可变的基础层 + 可回滚的补丁层。让系统只能改它被允许改的部分，且每次改动留快照， 用户才敢真的让它长期自治。反过来设计（模型自己改写自己的一切）只会在 第一次出错后就失去信任。另一个可抄点：把"沉淀工作方法"做成一等功能 （/refine），而不是藏在配置里。 AI + 开发持续观察
  • Progress AI Observability 如果你做质量评估类功能，参考"评估必须和产生它的执行路径绑定"—— 脱离轨迹的评分是摆设，用户无法判断分数可信。另一个可抄点：把"花费归因" 做成一级功能，因为成本是用户最容易感知的痛点，比"质量"更愿意付钱。 基础层持续观察
  • Qoder-阿里 长任务 agent 的核心问题是上下文丢失，解决办法不是加大窗口，而是"多角色各自独立上下文、最后汇合"。做复杂任务工具时，与其赌更大的上下文窗口，不如把任务拆给相互隔离的执行单元。 AI + 开发持续观察
  • Qwen.ai｜阿里 一个模型底座开三个入口——国内 App 做规模、国际站做触达、开源做生态——三个入口互相喂，不把增长押在任何一个上。做平台型产品时，比"一个入口做到极致"更稳的是"一个底座、多个入口、各司其职"。 AI + 效率持续观察
  • Reference 给 AI agent 做工具的，把"结果带回源引用"做成默认行为—— 每个答案都指回文件、函数、行号，让 agent 的输出可以被验证，而不是一段泛泛文本。 这既是技术特性，也是信任机制：用户（和 agent）只有能追到证据才敢用。 基础层持续观察
